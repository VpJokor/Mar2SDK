# Mar2SDK 使用文档

本文档对应当前仓库版本。SDK 是一个 Android 多模块工程，提供广告展示策略、广告平台封装、事件埋点、归因、风险辅助判断和应用通知能力。

## 1. 模块与运行要求

| 模块 | 用途 | 接入建议 |
| --- | --- | --- |
| `core` | SDK 核心、配置、广告策略、日志、Firebase/Singular/ThinkingData、通知和工具类 | 由 `impl` 间接依赖，一般不直接接入 |
| `impl` | 面向业务的封装，包含 `Mar2Application`、`BaseActivity`、`AdActivity` 和 Compose 导航广告组件 | 业务应用直接依赖 |
| `debug` | 调试页和配置查看工具 | 仅在调试包中依赖 |
| `app` | 仓库内的示例应用 | 用于验证 SDK 集成 |

当前工程要求 `minSdk 29`、`compileSdk 37`、Java/Kotlin JVM 11。SDK 依赖 Firebase、Google Mobile Ads、Singular、ThinkingData、Play Integrity 等服务，并在 `settings.gradle.kts` 中声明了相应 Maven 仓库。

## 2. 接入工程

如果 SDK 以源码模块接入，在应用模块的 `build.gradle.kts` 中添加：

```kotlin
dependencies {
    implementation(project(":impl"))
    // 仅调试需要时添加
    debugImplementation(project(":debug"))
}
```

当前仓库没有配置 Maven 发布坐标。对外提供时，需要先生成并发布包含 `core` 传递依赖的 `impl` AAR。

### 2.1 Application 初始化

最简单的方式是继承 `Mar2Application`。它会在 `onCreate` 中调用 `Core.init`：

```kotlin
class MyApplication : Mar2Application() {
    override fun onCreate() {
        super.onCreate()
    }
}
```

在 `AndroidManifest.xml` 中注册：

```xml
<application android:name=".MyApplication" ... />
```

`Mar2Application` 当前示例使用 `AppMod.DEBUG`。正式环境应按渠道选择模式：

```kotlin
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        Core.init(this, AppMod.RELEASE)
    }
}
```

`AppMod` 有 `DEBUG`、`TEST`、`PRE_RELEASE`、`RELEASE` 四个值。`DEBUG`/`TEST` 会强制使用 AdMob 内置测试广告位；正式广告位只在 `RELEASE` 下使用。\n\n如果要完全控制初始化模式，请直接继承 `Application` 调用 `Core.init`。不要在 `Mar2Application`（其 `super.onCreate()` 已经以 `DEBUG` 初始化）子类中再次尝试切换到 `RELEASE`。

初始化会加载配置并初始化广告、Firebase、Singular、ThinkingData、风险辅助模块、通知和应用状态监听。必须在调用其他 SDK API 前完成初始化。

`Core.init` 每次都会调用 `NetUtil.initLog()`，异步上报启动设备信息，无需先登录，也不受 `CommonConfig.isAutoLogin` 影响。请求读取 `CommonConfig.serverAppID`、`serverClientKey`、`serverUrl`、`initLogPath` 和 `Core.SDK_VERSION`，上报 `deviceID`、`channelID=0`、`deviceOS=1`、`deviceType=Build.MODEL` 和 `deviceDpi=densityDpi`，并自动添加公共 Header 和签名。上报失败会记录日志，不阻塞登录或启动。

无参 `NetUtil.initLog()` 返回 `Job`，可调用 `cancel()` 取消，或在协程中调用 `join()` 等待任务结束。如需手动调用，请在 `Core` 初始化完成后执行，并避免与启动时的自动上报重复。

### 2.2 Manifest、权限和服务

依赖 `impl` 后，Gradle 会合并 `AdActivity`、常驻服务和开机接收器。请检查最终合并后的 Manifest，至少保留以下能力：

- `INTERNET`、`ACCESS_NETWORK_STATE`、`WAKE_LOCK`
- Android 13 及以上的 `POST_NOTIFICATIONS`
- 开机恢复通知所需的 `RECEIVE_BOOT_COMPLETED`
- `FOREGROUND_SERVICE` 与 `FOREGROUND_SERVICE_SPECIAL_USE`

`impl` Manifest 默认提供测试用 AdMob `APPLICATION_ID`。发布前请替换为自己的 AdMob 应用 ID，并在 Firebase 配置中提供正确的 `google-services.json`。

## 3. 广告

### 3.1 Compose 导航广告（推荐）

`impl` 提供页面进入、返回和离开前的插屏广告封装。使用 `NavHost` 时，先注册路由跟踪器，再将需要广告的页面改为 `contentComposable`：

```kotlin
setContent {
    val navController = rememberNavController()
    ObserveScreenAdRoutes(navController)

    NavHost(navController, startDestination = "home") {
        composable("home") { HomeScreen() }
        contentComposable("detail") {
            val navigateWithAd = rememberNavigateWithAd(navController)
            DetailScreen(onNext = {
                navigateWithAd("result") { launchSingleTop = true }
            })
        }
        contentComposable("result") { ResultScreen() }
    }
}
```

行为如下：

- 首次进入页面请求 `${route}_start`；返回页面请求 `${route}_back`。
- 调用 `navigateWithAd` 时先请求 `${currentRoute}_leave`，广告结束后执行导航；广告无法启动时立即导航。
- 同一次页面停留期间的重复请求会被忽略。
- `ObserveScreenAdRoutes(navController)` 必须放在 `NavHost` 前，否则 `fromRoute` 无法正确记录。

如果页面没有使用 Navigation，也可以直接用 `BaseScreen { ... }` 包裹 Composable。预览模式会自动关闭广告请求。\n\n应用进入前台时 SDK 会自动预加载广告；如需手动预加载，可在协程中调用挂起函数 `AdLoader.fillAd()`。

### 3.2 View/XML 页面广告

传统 View/XML 页面可以继承 `com.mar2sdk.impl.ContentActivity`，并直接声明广告配置中的业务页面名。页面名必须使用配置中的原始名称，不要从 Activity 类名、反射结果或混淆名称推导：

```kotlin
class Content1Activity : ContentActivity() {
    override val screenName = "content1"

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_content1)
        findViewById<View>(R.id.next).setOnClickListener {
            navigateWithAd(
                toScreenName = "content2",
                intent = Intent(this, Content2Activity::class.java)
            )
        }
    }
}
```

`ContentActivity` 会自动处理以下广告位：

- 页面首次打开：`${screenName}_start`
- 从其他页面返回：`${screenName}_back`
- 跳转到其他页面前：`${screenName}_leave`
- 系统返回键：先展示当前页面的 leave 广告，再返回上一页面

业务 Activity 的页面跳转必须调用 `navigateWithAd(toScreenName, intent)`。它会在广告结束后启动目标 Activity，并通过 Intent 记录 `fromRoute`/`toRoute`；直接调用 `startActivity` 会绕过跳转前广告和来源路由记录。目标 Activity 仍应使用自己的 `screenName`，例如广告配置使用 `content2_start` 时声明 `override val screenName = "content2"`。

`ContentActivity` 使用现有插屏配置和 `AdConfig.defaultPlatform`，广告策略拒绝、广告正在展示、启动失败或 Activity 已销毁时会继续原页面操作。Activity 重建时会保存进入状态，避免重复请求 start 广告。现有 Compose 页面继续使用 `BaseScreen`、`contentComposable` 和 `NavController` 路由广告逻辑。

当前仓库中的 `DebugActivity`、`InfoActivity` 是调试页面，未强制迁移到 `ContentActivity`。业务 View/XML 页面可按上面的方式逐页迁移。

### 3.3 直接展示广告

需要自定义 Activity 或广告流程时，可使用 `AdActivity.showAd`。该方法返回 `Boolean`，表示广告页是否成功启动；真正的广告结果通过 `Core.showAd` 的回调返回。

```kotlin
val context = ScreenAdContext(
    areaKey = "home_leave",          // 必须与 ad_config.json 的键一致
    adFormat = AdFormat.INTER,
    adPlatform = AdConfig.defaultPlatform,
    trigger = ScreenAdTrigger.LEAVE,
    fromRoute = "home",
    toRoute = "detail"
)

val launched = AdActivity.showAd(this, context)
```

如果不使用 `AdActivity`，可以在协程中直接调用挂起函数。`Core.showAd` 本身只负责分发到广告展示器，不会自动执行 `AdPolicy`，请在调用前自行调用 `AdPolicy.canShowAd(context)` 或实现等价的频控判断：

```kotlin
lifecycleScope.launch {
    val status = Core.showAd(this@MainActivity, object : ShowCallback {
        override val adContext = context
        override fun showFailed(reason: ShowFailResult) { /* 处理失败 */ }
        override fun showSuccess() { /* 广告开始展示 */ }
        override fun onClicked() = Unit
        override fun onAdClosed() { /* 关闭 */ }
        override fun onPaid() = Unit
        override fun onReward() = Unit
    })
    Log.d("Ad", "show status=$status")
}
```

可用广告格式：`OPEN`（开屏）、`INTER`（插屏）、`VIDEO`（激励视频）、`OPEN_INTER`（开屏与插屏比价）、`INTER_VIDEO`（插屏与激励视频比价）、`VIDEO_INTER`（激励视频与插屏比价）。组合格式选择价格更高的广告；同价或任一价格缺失时优先选择名称中的第一种格式。等待另一种格式加载失败或超时后，仍可展示已有的有效广告。

AdMob 按每个广告加载时保存的 `probeConfig.mod` 选择反射价格或探针上界、中点、下界（`REFLECT` / `ADAPTER_H` / `ADAPTER_M` / `ADAPTER_L`），统一为 USD eCPM 微单位后比价；不同格式可以采用不同模式。单个缓存池选已知价格最高的广告，同价或全部未知时选最先缓存者。配置与缺价处理见 [`admob_config说明.md`](项目配置/admob_config说明.md)。

`AdShowStatus` 包括 `SHOW_SUCCESS`、`SHOW_FAIL`、`TIMEOUT`、`OTHER_AD_IS_SHOWING`、`LOAD_FAIL`。失败回调的 `ShowFailResult` 可区分加载失败、超时、已有广告、Activity 不可用和异常等原因。

### 3.4 广告平台现状

支持的平台枚举为 `ADMOB`、`MAX`、`UNITY`、`TRADPLUS`、`TOPON`。当前实际展示和加载逻辑主要实现了 AdMob；其他平台的初始化/展示仍有 TODO，部分分支会回退到 AdMob。配置 `activePlatforms` 不代表这些平台已经具备完整的竞价和展示能力，发布前请按实际实现验证。`Core.init` 只初始化 `defaultPlatform`；需要额外初始化活动平台时，再调用 `AdIniter.initActives()`。

### 3.5 Banner 广告

在主线程调用 `Core.getBanner(activity, callback, adSize)`，将返回的 `AdView` 加入页面容器。`callback` 使用上面的 `ShowCallback` 接口，建议每个 Banner 创建独立的回调和 `ScreenAdContext`，其中 `areaKey` 填写 Banner 点位。方法会将上下文的格式、平台和广告位 ID 更新为实际使用的 `BANNER`、`ADMOB` 和 `AdmobConfig.bannerID`。

```kotlin
// Activity 成员；bannerCallback 为该 Banner 的 ShowCallback。
private var banner: AdView? = null

// 页面创建后、主线程执行。默认尺寸为 AdSize.BANNER，也可传入自适应 AdSize。
banner = Core.getBanner(this, bannerCallback)
banner?.let { bannerContainer.addView(it) }

// 在对应的 Activity 生命周期回调中执行：
// onPause:  banner?.pause()
// onResume: banner?.resume()
// onDestroy:
banner?.let {
    (it.parent as? ViewGroup)?.removeView(it)
    it.destroy()
}
banner = null
```

返回 View 表示已开始异步加载；实际曝光时才触发 `showSuccess()`。加载失败通过 `showFailed(LOAD_FAILED)` 回调，Activity 已结束或启动加载异常时返回 `null` 并回调具体原因。Banner 自动刷新后可多次触发展示和收入回调，`onAdClosed()` 表示点击广告后打开的页面关闭。

Banner 使用 `bannerConfig.id`，DEBUG/TEST 模式使用内置测试 ID。该入口不执行全屏广告频控、等待或广告池逻辑，也不占用全屏展示锁；调用方决定 Banner 的展示时机。`BannerStyle` 暂无尺寸映射，通过 `adSize` 显式指定尺寸。`Core.showAd` 用于全屏广告，传入 `BANNER` 会返回 `SHOW_FAIL`。

### 3.6 原生广告

在页面协程中调用 `Core.getNative(activity, callback, adIndex = 0)`。方法按所选分组的高、中、低广告位顺序加载，返回已加载的 `NativeAd`；失败或超时返回 `null`，具体原因通过 `ShowCallback.showFailed` 通知。`adIndex` 是 `AdmobConfig.nativeConfig.ads` 的零起始索引，与 `NativeStyle` 无隐式映射。

```kotlin
// Activity 成员；nativeCallback 为该广告独立的 ShowCallback。
private var nativeAd: NativeAd? = null

lifecycleScope.launch {
    val loaded = Core.getNative(this@MainActivity, nativeCallback) ?: return@launch
    nativeAd?.destroy()
    nativeAd = loaded

    // nativeAdView 为页面的 NativeAdView；先填充并注册标题、媒体、按钮等素材 View。
    // 例如：headlineView.text = loaded.headline; nativeAdView.headlineView = headlineView
    nativeAdView.setNativeAd(loaded)
}

// 页面移除广告或 Activity.onDestroy 时执行：
nativeAdView.destroy()
nativeAd?.destroy()
nativeAd = null
```

调用方负责提供 `NativeAdView` 布局、绑定广告素材和释放返回的广告。应先注册并填充标题、媒体和行动按钮等素材 View，再调用 `setNativeAd`，布局需包含广告标识并预留 AdChoices 展示空间。页面加载任务应随页面生命周期取消；加载取消或超时后才返回的 SDK 广告由 SDK 封装自动销毁，已经返回的广告由调用方负责销毁。

`showSuccess()` 在实际曝光时触发，返回广告对象仅表示加载完成。点击、关闭和收入事件沿用 `ShowCallback`。每次请求会把上下文格式、平台和广告位 ID 更新为实际使用的 `NATIVE`、`ADMOB` 和当前档位 ID；建议每次请求使用独立回调及 `ScreenAdContext`。

原生广告使用 `nativeConfig.timeout` 作为高、中、低三档共享的加载预算，DEBUG/TEST 使用官方原生测试 ID。该入口不执行全屏广告频控或广告池逻辑，也不占用全屏展示锁。`Core.showAd` 接收 `NATIVE` 时返回 `SHOW_FAIL`，页面内原生广告应使用 `getNative`。配置细节见 [`admob_config说明.md`](项目配置/admob_config说明.md)。

## 4. 广告策略配置

默认配置位于 [`ad_config.json`](../core/src/main/res/raw/ad_config.json)，AdMob 配置位于 [`admob_config.json`](../core/src/main/res/raw/admob_config.json)。初始化时先读 raw 资源，再用本地 Preference 覆盖。运行时修改后调用对应的 `save*Config()` 才会持久化；修改 raw 文件需要重新打包。

`AdConfig` 的关键字段：

| 字段 | 说明 |
| --- | --- |
| `defaultPlatform` / `activePlatforms` | 默认平台和额外启用的平台 |
| `isOpen` | 全局广告开关 |
| `showMaxTime` / `showMinTime` | 展示流程的最长等待和最短等待（毫秒） |
| `1HMax` / `24HMax` / `interval` | 全局 1 小时、24 小时展示上限和两次展示间隔（秒） |
| `ad_units` | 以 `areaKey` 为键的广告位策略 |

每个 `ad_units` 项包含 `rate`、`1HMax`、`24HMax`、`interval`、`format`、`fromRoutes`、`toRoutes`。`rate` 范围为 0.0～1.0；路由必须完整匹配，使用 `"*"` 表示任意路由。全局策略和广告位策略都满足时才会展示广告，`areaKey` 必须与业务传入值完全一致。

AdMob 的 `releaseOpenID`、`releaseInterID`、`releaseVideoID` 请替换为自己的正式广告位。`openTimeout`、`interTimeout`、`videoTimeout` 单位为毫秒，`*PoolSize` 为缓存池大小。测试和调试模式始终使用 Google 官方测试 ID。

更多字段说明：[`ad_config说明.md`](项目配置/ad_config说明.md)、[`admob_config说明.md`](项目配置/admob_config说明.md)。

## 5. 日志、用户属性与归因

业务代码和 SDK 内部的日志、属性设置统一通过 `Core` 调用：

```kotlin
Core.log("content_open", mapOf("route" to "detail", "source" to "home"))
Core.setUserOnceAttr("first_channel", "organic")
Core.setUserAttr("vip_level", 2)
Core.setUserAttr(mapOf("network" to "organic", "fromNature" to true))
Core.setEventAttr("traffic_source", "desktop")
```

`Core.log` 会按 [`log_config.json`](项目配置/log_config说明.md) 的开关写入 Firebase、ThinkingData、本地数据库和预留的网络渠道。事件列表中的 `"*"` 表示该渠道接收全部事件。ThinkingData 日志还受 `thinking_config.json` 中 `logEndTime`（小时）限制。

SDK 会根据应用启动 Intent 自动设置 `traffic_source`：桌面图标启动为 `desktop`，普通应用通知（`AppOpenFrom=app_push`）为 `notification`，常驻通知（`AppOpenFrom=persistent`）为 `persistent_notification`，无法识别入口时为 `unknown`。调试 FCM 通知点击也会携带 `app_push`，因此按普通应用通知归类。该字段会随 SDK 事件写入 ThinkingData、Firebase、本地日志和服务端广告事件；业务也可以通过 `Core.setEventAttr` 覆盖 ThinkingData 的公共属性。

`Core.setUserAttr` 设置可覆盖的用户属性，支持单个键值或一次提交整组 `Map`；`Core.setUserOnceAttr` 设置只写一次的用户属性，值为字符串；`Core.setEventAttr` 设置 ThinkingData 公共事件属性，自动附加到后续事件，当前事件独有的参数通过 `Core.log` 的 `params` 传入。三个属性接口均写入 ThinkingData，并受 `logEndTime` 限制；Singular 和 Install Referrer 的归因属性也通过此统一入口提交。

SDK 在 `Core.init()` 完成数数初始化后，以及每次 Activity 恢复时，自动向 ThinkingData 更新布尔用户属性 `has_notification_permission`。取值来自 `NotificationUtil.hasNotiAccess()`，同时检查 Android 13 及以上的通知权限和应用通知总开关，覆盖授权弹窗结束、从系统设置返回后的状态变化。业务层无需另加打点；该属性同样受 `logEndTime` 限制。

SDK 会自动初始化 Singular 归因和 Firebase。请在 [`singular_config.json`](项目配置/singular_config说明.md) 与 `google-services.json` 中填入正式项目凭据；不要把测试项目的 Key/Secret 带入生产包。

## 6. 通知

Android 13 及以上必须申请通知权限：

```kotlin
private val notificationPermission =
    registerForActivityResult(ActivityResultContracts.RequestPermission()) { granted ->
        if (granted) Core.startFGS()
    }

NotificationUtil.reqNotiAccess(this, notificationPermission) { granted ->
    if (granted) Core.startFGS()
}
```

也可以使用 `NotificationUtil.hasNotiAccess()` 查询当前权限，使用 `Core.startFGS()` 或 `NotificationUtil.startFGS()` 启动常驻前台服务。通知策略由 [`notification_config.json`](项目配置/notification_config说明.md) 控制；[`notification_content.json`](项目配置/notification_content说明.md) 配置普通通知文案和点击路由，不控制常驻通知栏的四个按钮。

当前实现的 `getContent(scene)` 始终取 `contents` 的第一项，`Scenes` 和 `Languages` 尚未参与筛选；如果需要按场景或语言发送，请在发布前补充或确认业务层逻辑。通知总开关 `isSend` 默认关闭。

### 6.1 在 APP 模块覆盖常驻通知按钮

常驻通知的折叠和展开布局使用同一组字符串与图标资源。APP 模块提供同名资源即可覆盖 SDK 默认值，无需新增配置代码。

| 按钮位置（从左到右） | 字符串资源名 | 默认文案 | 图标资源名 |
| --- | --- | --- | --- |
| 第 1 个 | `common_notification_action_1` | Photos | `notification_photos` |
| 第 2 个 | `common_notification_action_2` | Files | `notification_files` |
| 第 3 个 | `common_notification_action_3` | Videos | `notification_videos` |
| 第 4 个 | `common_notification_action_4` | Recovered | `notification_recovered` |

在 `app/src/main/res/values/strings.xml` 的 `<resources>` 中添加需要覆盖的文案：

```xml
<string name="common_notification_action_1">清理照片</string>
<string name="common_notification_action_2">文件管理</string>
<string name="common_notification_action_3">清理视频</string>
<string name="common_notification_action_4">恢复记录</string>
```

多语言文案可放在 `app/src/main/res/values-zh/strings.xml`、`app/src/main/res/values-en/strings.xml` 等目录，并使用上述同名字符串；Android 会根据当前语言选择资源。

替换图标时，在 `app/src/main/res/drawable/` 添加同名 PNG、WebP 或 vector XML。例如，`app/src/main/res/drawable/notification_photos.xml` 会替换第一个按钮的图标；文件名不含扩展名的部分必须与表中的图标资源名一致。

可以只覆盖部分按钮或只修改文案、图标中的一项；未覆盖的资源继续使用 SDK 默认值。修改资源后重新构建并安装 APP，待常驻通知重新创建，或在 APP 前台调用 `Core.startFGS()` 刷新通知，即可查看效果。

### 6.2 配置常驻通知按钮跳转

常驻通知点击通过启动 Intent 传递 `AppOpenFrom = "persistent"`、`Scene = "persistent"` 和 `Route`。`Route` 区分大小写；示例 APP 的跳转映射如下：

| 点击位置 | `Route` | 示例目标 |
| --- | --- | --- |
| 第 1 个按钮 | `Action1` | Compose 页面 `content1` |
| 第 2 个按钮 | `Action2` | Compose 页面 `content2` |
| 第 3 个按钮 | `Action3` | `Content1Activity` |
| 第 4 个按钮 | `Action4` | `Content2Activity` |
| 通知主体 | `persistent` | Compose 首页 `main` |

以上目标是当前仓库的示例页面。宿主 APP 可修改 [`MainActivity.kt`](../app/src/main/java/com/mar2sdk/MainActivity.kt) 的 `openNotificationDestination(route, navController)`，将各个 `Route` 映射到自己的 Compose 路由或 Activity。按钮文案、图标与业务跳转分别配置，修改资源不会改变点击目标。两个 Activity 跳转示例通过 `ContentActivity.EXTRA_FROM_ROUTE` 记录跳转前的页面路由。

`MainActivity` 在 `onCreate` 和 `onNewIntent` 中接收点击，等待 `NavHost` 就绪且 Activity 进入 `RESUMED` 后分发；待处理路由写入 `savedInstanceState`，跳转完成后清空，避免旋转屏幕重复跳转。常驻通知分支只接受 `persistent` 来源及上表路由，普通 APP 通知按下一节的映射处理。SDK 的点击已记录标记仅用于埋点去重，不消费 APP 的导航事件。

每个按钮使用独立、稳定且带私有 action 的 `PendingIntent`，避免不同按钮相互覆盖。启动 Intent 使用 `NEW_TASK | CLEAR_TOP | SINGLE_TOP`，`PendingIntent` 使用 `UPDATE_CURRENT | IMMUTABLE`，以支持冷启动及已有入口 Activity 接收点击。

更新此逻辑后需重新构建并安装 APP，并在 APP 前台调用 `Core.startFGS()` 刷新已有通知，确保旧通知的 `PendingIntent` 被替换。

### 6.3 配置普通 APP 通知点击

普通 APP 通知使用 `notification_content.json` 中的 `Route` 指定点击目标。SDK 将其原样放入启动 Intent，并传递 `AppOpenFrom = "app_push"` 和实际发送场景 `Scene`；通知主体和卡片按钮共用同一个 `PendingIntent`，打开同一目标。示例 APP 支持以下映射：

| `Route` | 示例目标 |
| --- | --- |
| `/recoverPhotos` | Compose 页面 `content1` |
| `/recoverVideos` | Compose 页面 `content2` |
| `/recoverFiles` | `Content1Activity` |

例如，在 `app/src/main/res/raw/notification_content.json` 中配置：

```json
{
  "contents": [
    {
      "Title": "照片恢复",
      "Content": "点击查看可恢复的照片",
      "Button": "查看",
      "Scenes": ["screen_on_a"],
      "Route": "/recoverPhotos"
    }
  ]
}
```

APP 的同名 raw 资源会覆盖 SDK 默认文件，但本地 `Preference` 已保存的 `contents` 优先。当前 `getContent(scene)` 仍只取 `contents` 第一项，不按 `Scenes` 或 `Languages` 筛选；因此测试不同路由时应修改实际生效的第一项。修改配置不会更新已发布通知，需要重新发送；修改 raw 文件还需重新构建并安装 APP。

宿主 APP 可在 [`MainActivity.kt`](../app/src/main/java/com/mar2sdk/MainActivity.kt) 的 `handleNotificationIntent` 中调整来源与路由校验，在 `openNotificationDestination` 中配置业务页面。`app_push` 和 `persistent` 分别校验各自允许的路由；未知来源、未知路由或来源与路由错配时不导航，SDK 仍按原逻辑记录点击埋点。

普通通知复用常驻通知的冷启动、热启动、同路由再次点击及待处理请求恢复机制。启动 Intent 使用 `NEW_TASK | CLEAR_TOP | SINGLE_TOP`，已有入口 Activity 可通过 `onNewIntent` 接收点击，待界面就绪后完成跳转。

## 9. 常见问题

1. **没有展示广告**：确认已调用 `Core.init`，`AdConfig.isOpen` 为 `true`，`areaKey` 存在且路由、频控和 `rate` 均满足条件。
2. **启动广告页失败**：确认 `impl` 的 Manifest 已合并 `AdActivity`，传入的 Activity 未处于 finishing/destroyed 状态，并避免重复启动广告。
3. **正式包仍使用测试广告**：检查 `AppMod` 是否为 `RELEASE`，并确认 `admob_config.json` 中的 `release*ID` 已替换。
4. **通知不显示**：检查系统通知权限、`NotificationConfig.isSend`、通知渠道以及前台服务权限。
5. **Compose 页面没有自动请求广告**：确认页面使用 `contentComposable` 或 `BaseScreen`，且 `ObserveScreenAdRoutes` 在 `NavHost` 前调用。
